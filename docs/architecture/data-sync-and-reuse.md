# JevNews：数据同步、存储与开源复用方案

> 版本：v0.1  
> 日期：2026-09-19（UTC+8）  
> 对应需求：[产品需求基线 v0.2](../product-requirements.md)  
> 状态：第一版实现方案与可配置起点；本次仅更新文档，没有导入复刻源码、部署数据库或运行服务。外部接口依据文档核验，未进行实时负载、持续同步或构建测试。

## 1. 结论

采用 **官方 HN API + 后台共享增量同步 + PostgreSQL + 异步内容分析 + HN 风格网页**。

不让每位访客直接递归调用 HN 接口；不每 10 秒全量抓取文章、全部评论或重新跑 Jev；不把 HN HTML 网页的高频抓取作为主要数据管道。

第一版使用轮询，快速实现和监测；新内容与变更提示以 10 秒为检查起点，其他对象分层刷新。官方 Firebase 支持订阅变化，可在需要时替换部分轮询，但不取消补缺与校验。

```text
HN 官方 API
    ↓
共享同步进程：列表 / 新 ID / 变更提示 / 按需详情
    ↓
PostgreSQL：HN 数据、同步游标、任务、账号和规则
    ├── 可访问正文 → 抽取 / 去重 → 公共分析 → 预设排序
    ├── 私人规则 → 复用分析 → 有限专项判断 → 私人排序
    └── Web 服务 → HN 风格列表 / 评论 / 用户资料

浏览器通常只读取 JevNews；HN 写动作由用户回到 HN 完成。
```

## 2. API 来源与不能假定的能力

HN 官方接口以 Firebase 提供公开 item、用户、列表和变更数据；官方建议使用能监听变化的客户端。[S1] Firebase REST 也支持 Server-Sent Events。[S2]

| 来源 | 用途 | 边界 |
| --- | --- | --- |
| `/v0/newstories` | 快速发现最近投稿 | 当前列表最多 500 条，不能代替完整历史或断线补录。 |
| `/v0/maxitem` | 获取最大 item ID，用持久化游标发现缺失区间 | item 包含评论等类型，不是每个新 ID 都是文章；可能遇到暂不可用或无效记录。 |
| `/v0/topstories`、`beststories` | HN 源列表快照和补充候选 | 原始模式保留 API 顺序，不用本地公式重建“官方排名”。 |
| `/v0/askstories`、`showstories`、`jobstories` | 相应列表入口 | 官方文档描述为最多 200 条；不能据此承诺每个原站子页面和所有分页都精确一致。 |
| `/v0/updates` | 提示哪些 item 和 profile 应刷新 | 没有文档化的消费位点、重放或不丢事件保证，不当作可持久重放的变更日志。 |
| `/v0/item/{id}` | 标题、URL、正文/评论 HTML、分数、子评论 ID、状态等 | 外链文章完整正文需另取；评论子节点需要进一步读取。 |
| `/v0/user/{id}` | 公开 HN 资料 | 不是本站账号，也不是 HN 授权或登录接口。 |

以上为接口文档能力概述。[S1] 对 updates 采用提示而非可靠日志，是基于其未提供消费恢复契约而作出的防丢设计。

API 未提供官方发帖、投票、回复或登录写入能力。HN FAQ 说明排名还受公开票数和时间之外的因素影响，因此不能保证使用自制公式完全复刻排名、权限或个人状态。[S1][S3]

使用 HN 托管的 Firebase 读取接口，不意味着 JevNews 必须把自己的用户或规则也放到 Firebase；自有数据保存在 PostgreSQL。

## 3. 第一版刷新计划

下表是运行默认值，配置化调整；不是 HN 的强制要求，也不是已测得的最佳参数。

| 对象 | 初始策略 | 应避免的做法 |
| --- | --- | --- |
| newstories、maxitem、updates | 后台各约每 10 秒检查；多实例只能有一个有效调度者或持有租约 | 每个浏览器各自轮询；每次重拉全部已知 item。 |
| top、best、ask、show 列表 | 约每 30 秒更新 ID 与顺序快照 | 排名没变就重跑正文分析。 |
| jobs 列表 | 约每 60 秒 | 把招聘全部送入个性化评分。 |
| 新发现 item | 入队后尽快获取，限并发和总速率 | 将所有 ID 当作文章或无视低票内容。 |
| 活跃帖子详情 | 变化提示优先；另以约 1–2 分钟做陈旧校验 | 假设 updates 能提供不丢事件保证。 |
| 正在查看的评论树 | 先读缓存；过旧时后台刷新，约 30–60 秒 TTL；必要时按分支补取 | 每 10 秒递归所有历史讨论。 |
| HN 用户资料 | 按访问加载，约 15 分钟缓存起步 | 持续全量同步所有用户。 |
| 冷门旧帖、历史评论 | 按访问和特殊状态检查刷新，不常驻高频循环 | 无上限全历史扫描。 |
| 外链正文 | 初次抓取；必要时低频重验证、手动重试或检测版本更新 | 因 HN 分数或评论变了就重抓正文。 |
| AI 分析 | 内容哈希 / 模型 / 分析标准版本构成幂等键，有变化才重算 | 将每次页面访问或数据轮询当作 AI 任务。 |
| 前端 | 首次打开、用户刷新或切换视图取快照；可低频检查版本提示 | 后台同步一次，页面就自动跳位一次。 |

例如，500 条 item 每 10 秒全部重拉，一天是 `500 × 8,640 = 4,320,000` 次详情请求；而一个控制端点每 10 秒检查是 8,640 次。这只是请求次数示例，不代表 HN 实际投稿量或本服务实测负载。增量方案还会产生必要的详情、评论和补缺请求。

HN API 文档目前说明没有速率限制，但这不是无限吞吐、稳定性或 SLA 保证。[S1] 第一版仍设置并发上限、总速率、抖动、超时、指数退避和熔断。网页正文抓取单独限速；HN FAQ 也提醒快速请求大量网页可能导致 IP 被封，不能把 API 说明套用到网页抓取。[S3]

## 4. 不漏新投稿和不丢变更

### 4.1 启动

读取当前各官方列表，优先补齐基础浏览所需 item；保存当前 maxitem 和已知同步范围。历史回填作为低优先级任务，逐步覆盖最近 7 天，不阻塞在线新数据。

### 4.2 持续发现

newstories 用于快速通道；maxitem 增长区间用于补缺。抓取区间中的 item 并按 type 分类；评论可用于最新评论和线程缓存，但不因此进入文章分析队列。

持久化区分“已发现最高 ID”和“已连续处理到的 ID”，为失败、null 或暂时不可用的条目保留重试状态。不能只把游标直接跳到最新值，再丢掉中间失败项。重试必须有退避与上限，并记录未补齐的缺口，而不是永久卡住所有后续数据。

### 4.3 更新

updates 返回的 ID 只用于决定刷新对象。对正在排队或处理的同一对象短期合并请求；不能因为某 ID 曾经处理过，就永久忽略它后来出现的变化。

同一批 ID 重复出现在提示中不等于对象版本一定没变。定时陈旧校验、活跃内容回读和列表对账负责弥补遗漏。

### 4.4 重新连接

进程恢复后从数据库游标补追新 ID，重读各列表，优先刷新当前活跃对象。恢复期间提供最近可用快照并标明更新时间；不宣称恢复了离线期间的每一个历史排名状态。

### 4.5 删除、死亡与失效

已知 deleted/dead 状态优先传播到公开列表、详情缓存和相关索引。清理或隐藏与删除正文有关的公开片段，不从旧快照复活已知删除内容。外链正文缓存与具体 HN 投稿关系分开保存，同一链接的其他有效投稿不能被错误合并成同一条讨论。

## 5. 分离三种时钟

**HN 元数据时钟**：帖子、分数、评论、排序列表的变化。

**内容分析时钟**：正文可用性、抽取版本、公共分析和专项分析完成时间。

**用户阅读时钟**：用户打开了哪一份排序快照，在第几页、哪个评论分支。

这三个时钟不能混在一起。后台数据更快，不要求用户正在读的列表立即重排；元数据新鲜，不表示全文已经被理解；分析结果更新，不要求重新抓取所有 HN 数据。

快照携带视图、规则版本、生成时间和分页游标。More 使用同一快照，返回页面保留阅读位置。用户明确刷新或修改规则后再开始新快照。保留已知删除状态的即时覆盖，不能以快照稳定为由继续显示已知删除内容。

## 6. PostgreSQL 足够承担第一版

选择单套 PostgreSQL，是为账号、规则、游标和任务提供统一持久化，而不只是缓存 HN。

建议逻辑表如下，具体 SQL 和索引另行设计：

| 数据组 | 内容 |
| --- | --- |
| hn_items、hn_profiles | HN 原始字段、类型、父子关系、状态和最后同步时间；HN ID 与本站用户 ID 分开。 |
| hn_feed_snapshots | 官方列表的有序 ID 快照与读取时间。 |
| source_documents、fetch_attempts | URL、最终 URL、内容哈希、正文缓存、抓取范围与失败状态。 |
| article_analyses | 公共画像、证据引用、内容/模型/标准版本、用量和完成时间。 |
| presets、preset_versions | 七套预设和版本化规则。 |
| users、sessions、private_profiles | 本站账号、会话、原始要求与编译后的私人规则。 |
| user_item_state | hide、收藏、访问状态；明确不代表 HN 的投票或隐藏状态。 |
| personalized_evaluations、feed_snapshots | 有限专项判断、覆盖状态和稳定排序结果。 |
| sync_checkpoints、jobs、usage_counters | 同步位点、可重试任务、租约/去重和账号及全站用量。 |

部署起点可以是 `web + worker + postgres` 三个容器；web 与 worker 复用同一代码库但独立进程。任务需要持久化、唯一键、重试和运行者租约，不能仅用进程内定时器保存唯一进度。

不先引入 Redis、向量数据库、图数据库或消息集群。出现实际瓶颈后再添加，不能为新闻列表提前搭建完整 RAG 基础设施。

运行清理默认值：正文分析缓存保留约 30 天；普通元数据与分析记录保留约 90 天后按用途清理；用户规则和明确保存的状态直到用户删除或按公开保留政策处理。已删除来源的清理和账号删除优先于普通保留期限。清理证据后不得仍宣称能展示已不存在的原文依据。以上保留值需要在上线隐私说明中如实列出，可在上线前调整。

## 7. AI 成本与处理边界

公共分析按内容版本跨用户复用。公共预设可共享计算结果；个人状态和规则另叠加，不需要每个访问者重新读全文。

HN 的 ID、URL、正文版本、分析版本与用户规则版本不能混成一个缓存键：同一正文可以有多个投稿及不同评论；同一篇文章的新私人条件也可能需要新判断。

私人专项判断按产品需求的每日额度执行，记录实际输入用量。合并 HTTP 请求不会消除不同规则和候选的计算工作；不能用请求条数代替 token 或文章版本评估数作为唯一账单指标。

正文抽取失败、仅有标题、超过可支持长度或格式不支持时，保留未知与部分分析状态。第一版不通过付费代理、浏览器农场或绕过访问控制来追求全覆盖。

所有抓取地址与第三方文本都当作不可信输入：限制内网/回环/元数据地址、重定向、协议、体积和时间；渲染 HTML 需要清理；正文中的指令不能变成系统指令或工具调用。用户规则只转换成受控规则，不执行任意代码。

## 8. 开源 HN 复刻：可以复用，但不能当作完整成品

以下项目及其公开文档在 2026-09-19 查阅。没有执行安装、构建、依赖安全审计或像素差异测试。

| 项目 | 已核实的特点 | JevNews 的使用建议 |
| --- | --- | --- |
| [vercel/next-react-server-components](https://github.com/vercel/next-react-server-components) | Next.js App Router / React Server Components 的 HN 示例，MIT；当前查看的 package.json 包含 Next 14.2.35、React 18.3.1。[S4][S7] | 优先作为轻量 React 列表、详情和样式参考。不要原封不动部署或把示例依赖当作当前推荐版本。 |
| [clintonwoo/hackernews-remix-react](https://github.com/clintonwoo/hackernews-remix-react) | TypeScript / Remix / React，MIT；README 明确说明部分公开 API 之外的能力仅在内存实现。[S5] | 参考传统链接、表单和路由组织；模拟状态与认证不能充当真实 HN 集成或生产持久化。 |
| [nuxt/hackernews](https://github.com/nuxt/hackernews) | Nuxt HN clone，支持 SSR，MIT。[S6] | Vue/Nuxt 路线的可用参考；是否采用取决于团队栈和实际视觉还原成本。 |

已直接检查 Vercel 示例的 `components/header.tsx`：new/past/ask/show/jobs/submit 导航和 login 渲染为 span，并不是已经实现的完整导航和登录系统。[S8] 因此“看起来像 HN”与“功能已经像 HN”必须分别验证。

**实现倾向**：使用 Next.js/TypeScript 的受支持稳定版本建立 JevNews，优先移植适用的 MIT 示例组件和少量样式，不先把整个示例仓库当作不可修改的底座。补齐真实路由、注册、后台数据层、可访问性、错误处理和测试；选择具体依赖版本时重新核验支持与安全状态。

复用时记录来源及必要许可证声明，保留仓库现有 LICENSE，不覆盖为上游项目许可证。不要复制 YC 品牌让用户误认官方服务。本次没有向仓库导入任何第三方源码。

## 9. 与“99% HN”有关的明确差异

基础页面以 HN 原貌为准，但不是伪装为 HN 官方服务。本站注册只保存本站偏好和私人规则。

投票、回复、提交、标记等真实写动作回到 HN 页面执行。禁止用本地内存点赞改变显示分数、用本站用户伪造 HN 作者，或把点击箭头后的跳转显示成投票已成功。

HN 的评论 kids 顺序可复用，但公开数据不提供全部用户投票状态、权限或评论分值。历史榜单和某些原站页面没有完全对应的公开端点；第一版保留原站链接，不以近似结果冒充精确副本。

内容抓取、UI 复刻和代码许可是三件事：有开源前端不代表获得全部源内容的无限存储授权，也不代表能够访问 HN 的私有写接口。本方案不作法律许可范围保证。

## 10. 实现验证顺序

第一步：HN 风格页面与只读数据通路，验证列表、评论、正文链接、原站写操作跳转和错误回退。

第二步：持久化共享同步、缺口补追、删除传播、重启恢复和内容去重；监测实际请求负载与队列积压。

第三步：公共画像与七套预设，使用真实多类型样本检验“有内容”与“只会匹配关键词”的差别。

第四步：本站账号、私人规则编译、专项判断、额度和隔离。

这四步是依赖顺序，不是交付日期或进度承诺。实际代码实现不属于本次文档提交。
