# JevNews 产品需求基线

> 版本：v0.1  
> 整理日期：2026-09-19（UTC+8）  
> 仓库：`earayu/jevnews`  
> 路径：`docs/product-requirements.md`  
> 文档性质：记录已经确认的产品需求、已经认可的产品方向，以及尚需讨论的事项；不是完整开发规格或排期承诺。

## 1. 产品定位

JevNews 是围绕 Hacker News 构建、使用 Jev 辅助文章判断的阅读服务。核心价值不只是新闻摘要，而是按照用户认可的阅读标准，组织哪些内容更值得优先阅读。

阅读标准不仅包括主题，还可以包含对内容的要求和例外，例如：关注 Agent 与数据库；优先真实工程经验和实现细节；少看纯融资消息；不因为项目热度低就降低其阅读优先级。这里的具体标准是示例，不代表所有用户都使用同一套偏好。

当前产品分层可以概括为：

**平台主动理解文章并承担费用 → 提供 N 套预定义个性化供用户选择 → 注册用户可以使用私人个性化。**

## 2. 已确认的产品需求

以下需求应当保留。验收描述是据此整理的建议口径，具体边界在后续讨论中细化。

| 编号 | 已确认需求 | 含义与边界 | 建议验收口径 |
| --- | --- | --- | --- |
| C-01 | 平台默认主动进行文章理解 | 对平台支持的内容池，由服务方组织文章理解，不要求每位用户逐篇提交分析任务。内容池、理解深度和更新频率尚未确定。 | 支持范围内的文章可以由平台发起处理，形成供阅读服务使用的分析结果。 |
| C-02 | 平台承担默认文章理解费用 | 公共文章理解的费用由服务方承担，不以用户提供模型 API Key 为前提。这不等于已确定全部功能永久免费。 | 用户使用公共文章理解结果时，无需提供自己的模型 API Key。 |
| C-03 | 提供 N 套预定义个性化 | 由产品提供多套可选择的阅读标准。N 的数量、名称、标准内容和维护方式待确定。 | 存在多套可识别的预设；不同预设能够表达不同阅读优先级。 |
| C-04 | 用户可以选择预定义个性化 | 用户不必从零编写私人规则，就可以选择现有方案。选择入口、默认选项及是否允许组合多个预设待确定。 | 用户能够选择预设，并按所选标准阅读内容。 |
| C-05 | 支持私人个性化 | 用户可以使用自己的阅读标准，而不仅限于公共预设。私人规则不应默认公开。支持的表达范围、数量、保存和版本管理方式待确定。 | 不同用户能够拥有不同的私人规则，且私人规则不会默认对其他用户公开。 |
| C-06 | 私人个性化必须注册 | 注册是使用私人个性化的必要条件；具体登录方式和注册触发时机待确定。注册不等于已经决定收费。 | 私人个性化的正式使用与用户账号关联，未注册用户不能绕过该条件使用。 |

### 需求来源

核心分层来自用户明确提出的原话：

> “我觉得文章理解我们默认主动自己做自己付费；我们提供N个预定义个性化，用户可以选择；支持私人个性化但是必须要注册；”

## 3. 已认可的体验方向

这些方向已在讨论中获得肯定，应作为产品设计的出发点；不能据此推定此前提过的所有实现建议都已确定。

| 编号 | 已认可方向 | 仍未确定的部分 |
| --- | --- | --- |
| D-01 | 用户表达的是阅读标准，而不只是订阅关键词 | 自然语言输入的支持范围、规则如何展示、歧义如何处理、哪些要求属于硬过滤。 |
| D-02 | 按个人或预设标准排序，是重要体验方向 | 默认页面是否直接采用个性化排序、排序的具体目标与规则、是否与其他排序并列展示。 |
| D-03 | 精选、排序和高亮/标注可以并存，不是二选一 | 哪些能力进入第一版；精选入口、数量或门槛；高亮表达什么；说明展示到什么程度。 |
| D-04 | 服务形态需要兼顾用户使用门槛和平台成本 | 私人个性化的免费范围、额外分析额度、是否引入付费，以及是否另外提供 BYOK。 |

排序和精选的目标应围绕“对当前读者更值得优先看什么”讨论，不把一个笼统的分数包装成所有文章的客观质量结论。这是建议采用的产品解释，具体措辞和排序依据仍需确认。

## 4. 当前分层的使用流程草案

本节是基于已确认需求推导的建议流程，不属于已经确定的界面规格。

### 4.1 使用预定义个性化

用户打开服务，看到默认内容列表；选择一个预设后，列表按照该预设的阅读标准组织。预设可以说明自己的偏好，帮助用户理解为什么列表不同。

建议公共预设允许未注册用户直接体验，使注册不是初次了解产品的门槛。当前明确的硬性要求是“私人个性化必须注册”；公共预设的访问和选择状态如何保存，尚未单独确定。

### 4.2 使用私人个性化

用户选择私人个性化入口，按要求完成注册，然后创建、保存或使用自己的阅读规则。

建议提供“以当前预设为基础修改”的入口，同时保留是否支持从零创建的讨论空间。登录前是否允许试填要求或预览效果、是否必须复制预设、一个账号可拥有几套规则，都未确定。

### 4.3 公共和私人之间的关系

公共预设可以被很多用户使用；私人规则属于具体用户。私人排序并不必然要求每位用户重新分析全部文章。

建议优先复用公共文章分析，在已有分析无法满足私人要求时再考虑追加判断。是否追加、覆盖多少内容、费用与额度如何处理，仍需产品和技术共同确认。本文不承诺任意自然语言要求都能够立即、完整地执行。

## 5. 开发前优先确认的产品问题

### P0：决定第一版范围的问题

| 编号 | 待确认问题 | 需要作出的决策 | 为什么需要先确认 |
| --- | --- | --- | --- |
| Q-01 | 第一版内容池是什么？ | 是否仅限 Hacker News；覆盖哪些帖子类型；纳入最新、热门、Show HN 或其他候选；保留多长时间；外链文章、纯文本帖、项目主页和评论分别处理到什么程度。 | 决定产品能发现什么、每天分析多少内容，以及是否能实现低热度发现。 |
| Q-02 | “文章理解”第一版具体产出什么？ | 需要主题、内容形态、工程细节程度、推广/融资属性、证据摘录等哪些结果；是否生成摘要；是否分析评论；正文不足时如何表示未知。 | 决定哪些预设和私人条件能够被可靠执行，也决定公共分析成本。 |
| Q-03 | 第一批预设是哪几套？ | 确定 N、名称、阅读标准、正反例和例外；明确是单选切换，还是支持多个预设组合。 | 预设是用户不创建私人规则时的核心产品，而非占位分类。 |
| Q-04 | 私人个性化第一版支持到什么程度？ | 是现有维度的自然语言调整，还是允许开放式条件并触发追加分析；支持几套私人规则；如何保存、修改、重置；如何区分“少看”和“不要看”。 | 决定能力承诺、使用体验和随用户数增长的成本。 |
| Q-05 | 第一版交付什么阅读体验？ | 独立 Web 阅读器还是浏览器扩展，桌面与移动端的支持范围；默认入口和预设；排序、精选与高亮如何组合；是否保留原排序或最新视图；是否允许隐藏内容；如何处理相似内容和探索内容。 | 决定第一版究竟交付怎样的阅读器，而不只是一个后台评分系统。 |
| Q-06 | 更新节奏和异常回退是什么？ | 文章多久进入列表，何时完成分析；新文章待分析、正文获取失败、结果不确定或服务故障时如何展示；用户正在浏览时是否自动重排。 | 用户需要稳定、可理解的阅读体验，不能把“无法判断”直接当成“不值得看”。 |

### P1：公开发布前需要确认的问题

| 编号 | 待确认问题 | 需要作出的决策 |
| --- | --- | --- |
| Q-07 | 账号和私人规则如何关联？ | 登录方式；注册入口；跨设备保存；规则和用户数据的查看、删除方式；公共预设是否完全免登录。 |
| Q-08 | 免费范围、额度和预算如何界定？ | 注册后的私人个性化是否免费；追加分析是否限额；单用户及全站上限；超过额度后的体验；是否需要收费或 BYOK。平台承担公共理解费用这一决定保持不变。 |
| Q-09 | 阅读行为与反馈做多少？ | 是否支持已读、不感兴趣、收藏、判断纠错；点击是否代表已读；反馈只影响单篇还是修改长期规则；是否做基于已读历史的信息增量判断。 |
| Q-10 | 展示和保存哪些原文内容？ | 展示标题、链接、摘要、证据片段还是全文；来源标注；是否支持中文摘要或翻译；正文保存范围与期限。 |
| Q-11 | 如何判断第一版有效？ | 用怎样的样本检验预设差异、排序是否符合标准、是否漏掉值得读的文章；记录实际分析成本；确定延迟和可用性目标。具体指标及阈值尚未确定。 |

建议讨论顺序：先决定 Q-01 至 Q-04，明确“处理什么、理解什么、提供哪些标准、私人规则能做什么”；再用 Q-05 和 Q-06 确定界面与运行体验；最后补齐发布所需的账号、额度、数据和效果评价。

## 6. 供下一轮讨论的建议，不视为定案

### 6.1 预设候选

| 候选名称 | 示例阅读标准 |
| --- | --- |
| 工程实践 | 优先真实部署、故障复盘和架构取舍，降低缺少实现说明的概念介绍的优先级。 |
| Agent 构建者 | 优先 Agent 的工具调用、状态管理、评估和实际实现，区分演示与工程经验。 |
| 数据库深读 | 优先数据库内部机制、性能分析、存储设计与生产经验。 |
| 小项目发现 | 优先有具体实现、想法有趣的小项目，不把高热度设为入选前提。 |

这四项只是此前讨论中的候选，不代表 N 已确定为 4，也不代表它们已经成为正式预设。

### 6.2 私人规则能力的三个可选层次

| 方案 | 用户可以做什么 | 需要明确的限制 |
| --- | --- | --- |
| A：调整已有维度 | 使用自然语言修改主题优先级、内容类型偏好和已有维度的规则。 | 不能假装支持公共分析没有覆盖的细节条件。 |
| B：已有维度加有限专项判断 | 先复用公共分析；遇到特殊要求时，对限定候选追加判断。 | 候选范围、额外分析额度、等待状态和失败回退。 |
| C：开放式私人评估 | 接受较自由的阅读标准，针对这些标准处理更大的内容范围。 | 不能承诺无限分析；需要明确能力、额度、时延和费用。 |

这三项是讨论选项，不是套餐承诺或已定技术架构。

## 7. 本文没有确定的事项

**注册不是付费承诺。** 已定的是使用私人个性化必须注册；是否收费、何时收费、收费标准和免费额度都未决定。

**平台付费理解文章，不等于分析整个历史互联网。** 文章池、历史跨度、重分析频率和评论处理范围都待决定。

**预定义个性化不等于已经建立规则社区。** 公开发布私人规则、订阅他人的规则、规则作者体系和交易能力，均没有确定为第一版需求。

**BYOK 不是公共文章理解的前提。** 是否另外提供 BYOK 或自托管版本尚未决定，也不是当前需求基线的交付承诺。

**已认可多种体验，不等于第一版全部上线。** 原排序视图、自动去重、阅读历史、收藏、翻译、长摘要、文章问答和评论提炼等具体能力，需要单独确认。

**此前成本示例不是预算承诺。** 本文不把讨论中的假设单价、用户规模、文章数量和费用估算固化为需求或服务保证。

**本文不锁定技术实现。** Jev 的具体接口、模型版本、评分公式、抓取方式、数据库、任务调度、缓存策略、前端框架和部署方案另行设计。文章分析的共享复用是成本优化建议，不意味着任意私人要求都能完全复用公共结果。
