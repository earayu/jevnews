# JevNews 产品需求基线

> 版本：v0.2  
> 更新日期：2026-09-19（UTC+8）  
> 仓库：`earayu/jevnews`  
> 状态：已确认需求 + 用户授权制定的第一版方案；不是功能已完成或上线声明。  
> 数据与复用设计：[数据同步与开源复用方案](architecture/data-sync-and-reuse.md)

## 1. 产品定位

**一个外观和阅读操作尽可能保持 Hacker News 原样，但允许用户选择阅读标准的独立网页服务。**

JevNews 不只是新闻摘要工具，也不另建一个与 HN 分离的投稿、投票和评论社区。内容来自 HN，平台主动分析内容；用户选择公共预设，或注册后建立自己的私人阅读标准。精选、排序和轻量高亮在同一份列表中工作。

用户的阅读标准不只是主题关键词，还可以包括内容形态、实现细节、经验和证据、难度、偏好和例外。排序表达的是当前阅读优先级，不宣称给文章提供客观、通用的质量结论。

## 2. 决策状态与已确认要求

- **用户确认**：用户明确提出的产品要求，保留为硬约束。
- **受托决定**：用户本轮授权由产品方案制定者决定的第一版设计，可据此实现，不再保持为开放选项。
- **运行默认值**：供实现和测试使用的起始参数，可通过配置调整，不是对外服务保证。
- **接口约束**：公开接口不提供的能力必须说明，不能用假按钮或本地模拟冒充 HN 的真实功能。

## 3. 内容池和第一版范围

### 3.1 纳入内容

默认来源仅限 Hacker News。持续发现新的顶层投稿，包括普通外链文章、文本帖、Ask HN、Show HN 和投票帖；热门榜单是补充入口，不是唯一入口。招聘数据用于保持 HN 的 jobs 和原始浏览体验，默认不参与七套阅读预设的 AI 排序。

每一条有效的新投稿均可进入平台处理流程。高票数可以影响处理的即时优先级，但不能使低票内容长期得不到处理。死帖、删除帖和重复抓取不作为正常有效内容反复分析。

### 3.2 阅读与分析不是同一个范围

| 对象 | 第一版阅读能力 | 第一版 AI 分析 |
| --- | --- | --- |
| 普通外链文章 | 标题跳转原网站；保留 HN 讨论入口 | 分析可获取的主要正文。 |
| 文本帖、Ask HN | 在详情页展示帖子和评论树 | 分析投稿文本，不因缺少代码而自动评价为差。 |
| Show HN、项目主页 | 保留项目链接和 HN 讨论 | 分析可获取的项目说明或 README；不承诺执行项目或审计全部代码。 |
| HN 评论 | 支持树状阅读、折叠、永久链接和回到 HN | 第一版不做全评论树摘要、评论排序或争论结论判断。 |
| 招聘、投票 | 尽可能保留原站阅读语义，写操作回 HN | 招聘默认不参与个性化阅读排序；投票不生成或修改选项和票数。 |
| PDF、音视频、登录墙等 | 仍可作为帖子浏览和跳转 | 第一版不承诺 OCR、音视频转写、多模态解析或绕过访问限制；内容不足时标注分析范围。 |

### 3.3 时间范围

个性化排序默认使用最近 7 天已发现的有效投稿，按 HN 投稿时间计算新鲜度，不把旧文章的新投稿误称为文章首次发表。原始 HN 浏览不受个性化候选时间窗限制。

首次部署先载入当前官方列表，再限速回填近期内容；补齐前显示实际覆盖起始时间，不声称已经收齐最近 7 天。运行后通过持久化同步游标发现新内容并补缺。第一版不做整个 HN 历史的全文理解。

## 4. 平台具体理解什么

分析结果是按一套可版本化标准得到的公共画像，可被全部预设和私人规则复用。原始来源数据、公共判断、用户规则和最终排序分开保存。

| 分析组 | 第一版产出 | 使用边界 |
| --- | --- | --- |
| 主题 | AI/Agent、数据库、系统、软件工程、安全、硬件、科学、数学、设计、产品、创业、历史等多标签，以及能可靠识别的技术实体 | 不以标题出现某词作为充分证据；主题可以并存。 |
| 内容形态 | 教程、原理解释、工程经验、故障复盘、基准实验、研究、项目介绍、产品发布、行业消息、随笔、提问 | 类型不是好坏；融资或发布消息中仍可能包含值得读的内容。 |
| 实现与解释深度 | 从只有结论或介绍，到具体步骤、机制，再到约束和取舍的有描述等级 | 分维度判断；不把长、专业术语多、代码块多直接等同于深入。 |
| 经验与证据 | 是否包含作者实际操作描述、实验方法、测量条件、日志、案例、来源引用 | 表示观察到这些材料，不等于验证结论正确、数据真实或基准公平。 |
| 阅读门槛 | 入门、需要背景、专业深入；正文长度等可直接计算的信息 | 不将专业文章自动排在入门文章之前；由预设决定。 |
| 内容目的 | 主要是解释、经验分享、展示、推广、融资/商业消息还是预测；允许混合 | 降低“只有宣传”的优先级，而不是一律排除公司博客或创业话题。 |
| 可识别重复 | 规范化 URL、正文哈希、同一材料的重复投稿关联 | 第一版不声称已经实现相对于用户全部阅读历史的语义信息增量判断。 |
| 可用性与来源 | 抓取成功/部分成功/失败、正文覆盖范围、抓取时间、内容版本、分析版本、可回查的原文片段或片段引用 | 未知不是否；不完整分析不得用完整分析的口吻解释。 |

文本提取、实体识别、证据定位和自然语言规则编译可以使用程序或独立模块；不把所有工作都默认视为 Jev 自带的自由文本生成能力。需要证据时优先保存和选择原文片段，不生成无法核对的引文。

对外默认不显示 0–100 的“质量分”。优先使用少量事实性标签和模板化依据，例如“匹配：数据库、故障复盘”。标注“有实验方法”不等于“实验已验证”。

只因 HN 票数、排名或评论数变化，不重新分析未改变的正文。正文版本或分析标准变化，才按策略安排重分析。

## 5. 首批七套公共预设

公共预设无需注册即可切换，第一版为单选；多个预设的自由混合留给私人规则，不另做复杂组合面板。首次访问默认 Balanced；之后记住用户选择，匿名用户仅保存在当前浏览器，注册用户可保存到账户。

这些预设是产品设计，不宣称是对 HN 用户群体的调查分类。HN 的范围不仅是编程或创业，其官方指南也强调满足知识好奇心。[S3]

| ID / 界面名称 | 阅读标准 | 重要例外 |
| --- | --- | --- |
| balanced / Balanced（综合） | 跨主题寻找有解释、经验、证据或独特观察的内容，控制重复与单一话题占比 | 不把“技术深度”作为科学、历史、设计或生活观察的唯一质量标准。 |
| engineering / Engineering（工程实践） | 优先真实部署、故障复盘、性能改进、架构取舍和有实现过程的经验 | 小规模实践也有价值，不强制大厂、生产事故或高流量背景。 |
| ai-builders / AI & Agents（AI 构建） | 优先 AI/Agent 的实现、评估、工具、失败案例、成本和运行经验 | 模型发布若提供方法、实验或可用能力仍可优先，不只接收负面复盘。 |
| systems / Systems & Databases（系统与数据库） | 优先数据库、存储、分布式系统、操作系统、网络及其原理、实现和测量 | 高质量解释型文章可优先，不必附带开源项目或真实事故。 |
| builders / Show & Build（项目发现） | 优先具体可查看或可尝试的项目、工具和有实现的新奇想法，主动覆盖低热度投稿 | 不限于 Show HN 标题；不开源不等于没有价值；平台未实际运行的项目不标为已验证可运行。 |
| startups / Products & Startups（产品与创业） | 优先产品构建、用户研究、商业模式、定价、获客和一手创业经验 | 不一刀切排除融资；重点降低只有金额、宣传和口号、缺少可学习信息的内容。 |
| curiosity / Curiosity（知识探索） | 优先科学、数学、硬件、历史、设计等有解释和独特观察的材料，增加跨主题发现 | 不要求贴近工作，也不把“与软件工程无关”当作降权理由。 |

公共预设按版本维护并显示简短标准。私人规则从预设复制后保留当时版本，不因平台修改公共预设而被静默改变。

## 6. 私人个性化能力边界

### 6.1 用户体验

注册后可从预设复制，也可以从零用自然语言创建。系统展示原始要求与可执行规则，用户保存后才生效。支持修改、重置和删除；规则默认私人，不进入公共市场。

第一版支持主题偏好、内容形态、深度和门槛、偏好/排除、条件例外，以及有限的专项语义条件。例如“少看融资，但有架构细节的保留”。

不因一次点击、停留或隐藏就自动改变长期规则。“已访问”不等于“已读完”；第一版不做隐式用户画像学习。

### 6.2 两层执行

**公共维度可满足的要求**：直接组合已有判断并重排，不让每个用户重复阅读全部正文。

**公共维度不足的专项要求**：对有限候选追加判断。例如“不依赖 Redis 且解释了恢复机制”。先用已有主题和内容信息建立候选，追加检查后标明覆盖范围。没有被复判的文章不能宣称已经满足专项条件。

无法从现有内容判断的要求显示为“未知”或“当前不支持”。用户明确要求“必须满足”时，匹配列表只纳入已得到足够依据的结果，同时提供未知/未评估数量和查看入口，不静默把未知当作已匹配，也不把它说成确定不符合。

不支持无限网络研究、私有仓库访问、代码执行、自动核实所有技术结论、全历史回溯或开放式代理工作流。

### 6.3 运行默认值

以下是防滥用和成本起点，可配置调整，不是付费套餐：

| 项目 | 第一版默认值 |
| --- | --- |
| 每账号私人规则 | 最多 3 套，同时使用 1 套 |
| 每套专项语义条件 | 最多 3 个；普通主题和排序偏好不因此变成专项任务 |
| 新增专项复判额度 | 每账号每日最多 100 篇文章版本的评估组；每组最多包含 3 个条件；新规则版本需要重新核算，缓存命中不重复计费 |
| 创建/修改并编译规则 | 每账号每日最多 20 次；浏览、切换已有预设和读取缓存不计入 |
| 全站保护 | 单独配置 token/任务/并发预算与熔断，不能仅依赖注册门槛 |

达到额度时保留基础排序和已有结果，明确说明哪些专项条件未继续评估；用户可以主动切回基础排序，不静默放松硬性条件。不出现支付引导，暂不收费。

## 7. 第一版阅读界面

### 7.1 保持 HN 原貌

以 HN 的橙色顶部栏、浅色背景、紧凑文本列表、编号、小箭头、标题与域名、灰色元数据、树状评论、普通文本链接和 More 翻页作为视觉和交互基线。保持原文标题和默认英文 UI；不默认翻译或改写标题。[S2]

不新增卡片流、大封面、仪表盘、侧边栏或聊天式首页。不改为无限滚动。除自有品牌、必要账号区别和明确的新功能外，基础页面尽可能逐项对齐。

使用 JevNews 名称和自有标识，不让用户误以为在 HN 官方域名或使用同一套账号。页脚说明独立服务和数据来源。

### 7.2 最小新增控件

在原有顶部导航下方增加一行紧凑控制：

`view: HN | Jev   preset: Balanced ▾   all | picks   my rules`

这只是文案与控件结构，不是精确的最终像素规格。窄屏允许自然换行，不引入新的大型导航结构。

默认首页为 Jev / Balanced；可一键切回 HN 源列表顺序。关闭新增标注后，基础列表不应被额外摘要撑高。

每篇至多默认展示少量短标签或重点标记；需要原因时点击展开，不给每篇常驻长解释。分数和评论数始终显示 HN 数据，不用 Jev 的匹配结果替换 points。

### 7.3 精选和列表排序

“all”展示该视图完整的候选列表，More 继续翻页；“picks”缩小到满足较高匹配要求且分析充分的内容，结果不足时不凑固定篇数。

个性化排序使用内容匹配、内容形态适配、新鲜度和有限社区信号，并进行同源重复控制和主题多样性处理。低票不是排除条件，不能只把 HN top 列表重排后宣称实现了冷门发现。

HN 原始模式保持官方接口提供的列表顺序，不用自写热度公式冒充 HN 排名。个性化模式允许有明确标记的探索内容；探索不能覆盖用户的明确排除规则。

同一轮浏览及 More 翻页使用稳定快照，避免重复、漏项和滚动中跳位。后台更新完成只显示小型“有更新”入口，用户刷新或切换规则后再使用新顺序。

## 8. HN 行为兼容与账号边界

HN 官方公开接口提供读取数据，并未提供账号登录、投票、发帖或回复的官方写接口。HN 排名还包括公开票数和时间之外的因素，不能只靠公式精确重建。[S1][S2]

因此，“99% 相似”不能解释为能够无条件复制 HN 登录态、权限、个人投票记录或全部站内动作。以下作为第一版接口约束下的默认处理，属于需要用户理解的显式差异。

| 操作 | JevNews 第一版行为 |
| --- | --- |
| 点外链标题 | 正常前往原站，保留浏览器普通点击、在新标签打开等语义。 |
| 点评论数、时间或文本帖 | 在本地读取 HN 帖子和评论；保留回到 HN 的永久链接。 |
| 评论树 | 按 HN API 的 kids 顺序展示，支持折叠；不自行重排，不编造评论分数或投票权限。 |
| 点作者 | 展示 HN 公共资料或前往 HN 用户页，不混同本站账户。 |
| hide、收藏、预设和私人规则 | 属于 JevNews 阅读状态；明确不写回 HN。匿名可保存当前浏览器状态，注册后支持账号保存。 |
| upvote、reply、submit、flag、投票选项 | 前往 HN 对应页面，由用户在 HN 登录并操作；不后台代投票，不显示本地假成功。入口提示动作将在 HN 完成。 |
| login / register | 进入 JevNews 自己的账号页；注册只创建本站账号，不创建 HN 账号。 |
| past、全站 comments、特殊列表或未精确支持的页面 | 保留入口，必要时明确跳转 HN 原页；不把近似列表冒充完全相同的历史或权限视图。 |
| 搜索 | 第一版保留 HN Search 的跳转体验，不把搜索服务当作全部实时数据的权威来源。 |

注册页延续 HN 的简洁表单风格；第一版采用用户名和密码的本站账号，邮箱作为可选找回渠道。具体认证库另行选择，不自行设计密码算法，不接收 HN 密码或 Cookie。本站账号数据应支持删除。

若将来要求在本站直接完成 HN 真实写操作，必须单独验证可支持的授权和写入方式，作为独立技术与产品变更；不能声称现有公开 API 已满足。

## 9. 同步和异常体验

正式服务采用 **官方 HN API → 后台共享同步 → 自有数据库 → 页面读取**。调用 API 与定期同步不是二选一：API 是来源，同步是把来源更新到本地的方式。

第一版以轮询实现：新投稿、最大 ID 和变更提示约每 10 秒检查；榜单按较低频率更新；详情按新 ID、变化、访问和陈旧程度补拉。具体计划见配套数据方案。

数据新鲜度和 AI 分析时延分开显示。10 秒是后台部分检查的起始周期，不是页面必须每 10 秒跳动，也不是文章理解必定在 10 秒内完成的承诺。

| 状态 | 展示与处理 |
| --- | --- |
| 已有元数据，正文或分析待完成 | 文章可进入原始浏览；在 Jev 视图明确标记待分析，不以零分当作差内容。 |
| 只能取得标题、简介或部分正文 | 展示有限判断及分析范围；不声称读过全文。 |
| 上游暂时不可用 | 使用最后成功快照并提示更新时间；保留 HN 原站链接，退避重试。 |
| 某条判断失败或额度用完 | 基础阅读和已有分析继续工作，未执行的条件明确说明。 |
| 正文或规则更新 | 异步生成新版本；旧结果注明版本状态，不静默套用新规则标签。 |
| 已知 deleted/dead | 按相应状态隐藏或展示必要占位，清理对应公开缓存，不能让旧快照继续复活已知删除内容。 |
| 页面浏览中获得新结果 | 提示更新，不自动改变当前排序和滚动位置。 |

## 10. 存储与成本边界

第一版采用一套 PostgreSQL，保存 HN 数据缓存、分析结果、预设版本、私人规则、账号状态、同步游标和任务。无需一开始引入向量库、图数据库、Redis、Kafka 或独立搜索集群。

外链主要正文用于内部分析，第一版不提供全文镜像阅读服务；默认保留近期分析需要的正文，具体清理策略见配套数据方案。URL、抓取状态和内容版本分开管理，避免同文重复付费。

后台任务必须可持久化、重试和去重；页面打开不触发全站重复分析。公开画像和公共预设结果跨用户复用，私人规则和私人状态按用户隔离。

暂不收费、无默认 BYOK。免费不等于无并发、无 token 上限或无限历史处理。

## 11. 第一版不做

不另建本地投稿/评论社区或本地票数体系；不托管 HN 登录凭据；不承诺 HN 官方写操作无跳转。

不做全文翻译、长摘要、文章聊天、全评论树 AI 分析、相对于全部已读历史的语义去重、规则公开市场、自动学习用户偏好、移动原生 App、默认 BYOK 或收费套餐。

这些并非永远排除，只是不阻塞第一版核心：HN 原样阅读、七套共享预设和注册后的私人规则。

## 13. 仍需验证，而不是继续悬空的产品题

七套预设、分析维度、私人能力边界、独立网页、原样 UI 和暂不收费已经可以据此推进。下一步重点是实现验证：页面对照、真实样本分析效果、同步负载、正文覆盖率和专项判断成本。

公开发布前仍需确定部署位置、域名、全站月度预算、运营联系方式、隐私说明和具体认证实现。运行额度、排名权重、阈值和同步频率应通过样本与压测调整。

唯一明显偏离“所有行为都像 HN”的地方是官方写操作和账号身份边界，已在第 8 节显式说明。本版不把这个限制掩盖成已完成的原生兼容能力。
